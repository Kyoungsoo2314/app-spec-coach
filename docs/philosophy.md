# 설계 철학

## 사용자에게는 쉽게, 내부에는 엄격하게

사용자는 DB·API·권한 모델을 몰라도 된다. Skill은 실제 업무 장면을 질문하고, 답을 내부적으로 데이터·상태·화면·검증 기준으로 정리한다.

## 명확해지기 전에 만들지 않기

짧은 요청을 곧바로 구현하면 모델이 빈칸을 대신 채운다. 그 결과 사용자가 원하지 않은 기능과 운영 조건이 코드에 굳어진다. 명세 코치는 이 빈칸을 숨기지 않고 대화로 줄인다.

## 계획보다 계약

좋은 계획은 시작점이다. 완료를 판단하려면 “무엇을 실제로 확인하면 되는가”가 필요하다. 그래서 SPEC과 구현 계약, 실제 검증 결과를 함께 둔다.

## 이미지보다 의도

이미지는 초보자에게 화면의 분위기와 정보 배치를 빠르게 보여줄 수 있다. 그러나 이미지 생성 모델은 확정되지 않은 기능을 임의로 그릴 수 있다. 따라서 이미지가 요구사항의 진실의 기준이 되지 않도록 한다.

## 모델보다 행동

모델은 바뀔 수 있다. 핵심 자산은 모델 이름이 아니라 인터뷰 순서, 상태 저장, LOCK 경계, 범위 보호, 검증 규칙이다. 모델이 바뀌어도 문장 일치가 아닌 행동 계약으로 품질을 다시 확인한다.

## 코어와 배포 채널 분리

Skill이 코어이고 GitHub는 배포 채널이다. Plugin이나 독립 앱은 후속 배포 채널이 될 수 있지만, 하나의 채널이 막혀도 인터뷰 규칙과 eval을 잃지 않도록 한다.
