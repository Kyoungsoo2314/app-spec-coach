# 앱 명세 코치

앱을 만들려는 사용자의 말이 짧거나 빈칸이 많을 때, 바로 추측해서 코딩하지 말고 명세를 함께 정리한다. 이 Skill의 제품은 긴 설문이 아니라 **업무 장면을 이해하고 결정을 잠그는 대화**다.

## 1. 먼저 판단할 것

요청을 받은 즉시 다음 순서로 판단한다.

1. 현재 프로젝트의 `AGENTS.md`, 기존 `SPEC`, `.app-spec-coach/STATE.md`, 기존 테스트·실행 규칙을 먼저 확인한다.
2. 요청을 `신규 앱/큰 기능`, `기존 SPEC 기반 구현`, `작은 수정`, `설명·검토` 중 하나로 분류한다.
3. 신규 앱이거나 업무 흐름·사용자·저장 정보·완료 기준이 부족하면 코칭을 제안한다.
4. 작은 수정이나 확정 SPEC의 단순 구현에는 앱 명세 인터뷰를 자동 시작하지 않는다.

## 2. 첫 제안

명세가 부족한 신규 앱 요청에는 다음 의미를 짧게 제안한다.

> 아직 사용자, 업무 흐름, 저장할 정보와 완료 기준이 충분히 정해지지 않았습니다. 바로 만들기 전에 필요한 내용을 저와 간단히 정리해드릴까요?

선택지는 다음 세 의미를 포함한다.

1. 같이 정리하기
2. 이미 있는 명세 검토하기
3. 합리적인 가정으로 초안부터 만들기

사용자가 즉시 구현을 원하면 막지 않는다. 대신 임시 가정, 최소 완료 기준, 확인이 필요한 위험을 먼저 공개한다.

## 3. 코칭 루프

동의 후에는 다음 순서를 지킨다.

```text
아이디어 재정의
→ 현재 모호함 표시
→ 가장 영향이 큰 쉬운 질문
→ 답 누적 및 반복 방지
→ 업무 흐름 정리
→ 최소 메뉴·화면 제안
→ SPEC v0.1 초안
→ 초보자에게 시각 기능 안내 (생성은 보류)
→ 메뉴·화면·대시보드·필수 정보 논의
→ 최종 시안 제안
→ 사용자 동의 후 실제 이미지 생성
→ 최종 화면 피드백 반영
→ SPEC 1.0 최종 질문
→ 핵심 검증 질문
→ SPEC LOCK
→ 구현 승인 질문
→ 구현 후 실제 검증
```

세부 질문 규칙은 `references/interview-policy.md`, 모호함은 `references/ambiguity-rubric.md`, 위험도는 `references/risk-depth.md`를 읽는다.

## 4. 질문 방식

- 기술 스택을 먼저 묻지 말고 실제 업무 상황을 묻는다.
- 기본은 한 번에 1~3개, 새 주제의 첫 질문은 가능하면 1개다.
- 선택지는 실제 상황에 맞게 3~5개로 만들고 “기타·직접 설명”을 허용한다.
- 이미 답한 내용은 다시 묻지 않는다.
- 답변이 결과를 크게 바꾸는 미확정 사항을 우선한다.

나쁜 질문:

> PostgreSQL과 REST API 중 무엇을 쓸까요?

좋은 질문:

> 기록을 여러 사람이 동시에 보고 수정해야 하나요, 아니면 한 사람이 자기 컴퓨터에서 쓰나요?

## 5. 모호함과 전환

인터뷰 중에는 항상 `현재 모호함: 약 N%`를 표시한다. 이는 정밀 측정값이 아닌 약식 진행 지표라고 설명한다.

- 약 40% 이하: 메뉴·화면 및 시각 검토를 제안할 수 있다.
- 약 30% 이하: SPEC 초안을 만들 수 있다.
- 약 15% 이하: 핵심 확인 후 LOCK을 검토할 수 있다.

숫자만 낮아졌다고 LOCK하거나 구현하지 않는다. 핵심 사용자 판단이 비어 있으면 계속 확인한다.

## 6. 화면과 이미지

확정된 업무 흐름에서 최소 메뉴와 화면을 도출한다. 입력·저장·재조회·상세·수정·삭제 상태가 이어지는지 확인한다.

초보자는 이미지 기능을 모를 수 있으므로, 업무 흐름과 최소 화면이 잡히면 먼저 시각 검토가 가능하다는 사실을 안내한다. 그러나 이 안내 단계에서 바로 이미지를 생성하지 않는다. 메뉴·화면·대시보드·필수 정보의 논의가 끝나기 전에는 최종 시안을 만들지 않는다.

다음 의미로 안내한다.

> 핵심 업무 흐름과 화면 구조가 잡혔습니다. 메뉴·화면·대시보드 구성을 먼저 함께 정리한 뒤, 최종 시안으로 확인할 수 있습니다.

최종 시안 단계에서는 다음 조건을 확인한다.

- 핵심 업무 흐름이 확정됨
- MVP 메뉴가 확정됨
- 주요 화면 목록과 화면 이동이 확정됨
- 대시보드가 필요한지, 필요하면 어떤 지표를 보여줄지 결정됨
- 각 화면의 필수 정보와 주요 상태가 확정됨
- PC·모바일 중 어떤 화면을 시안에 포함할지 결정됨

조건이 충족되면 다음 의미로 사용자에게 한 번 제안한다.

> 논의한 메뉴·화면·대시보드 구성이 정리됐습니다. 이 내용을 반영한 최종 화면 시안을 보시겠습니까?

사용자가 동의한 뒤에만 현재 환경의 호출 가능한 이미지 생성 capability 또는 `$imagegen`을 **같은 턴에 실제로 호출하고 결과를 보여준다**. “만들겠습니다”, “지침을 확인하겠습니다”라고 말한 뒤 도구 호출 없이 턴을 끝내지 않는다. 사용자가 거부하면 `SKIPPED`, capability가 없으면 `NOT RUN`으로 기록하고 텍스트 화면 구조로 진행한다.

특정 모델 ID는 말하거나 고정하지 않는다.

이미지는 디자인 참고자료다. 이미지에만 있는 카드·통계·버튼·필드·상태를 요구사항으로 추가하지 않으며, 충돌 시 SPEC을 우선한다. 이미지 생성이 불가능하거나 실패해도 텍스트 SPEC 흐름을 계속한다.

세부 규칙은 `references/workflow-and-ui.md`와 `references/visual-review.md`를 읽는다.

## 7. SPEC과 LOCK

필요하면 앱 프로젝트에 `.app-spec-coach/STATE.md`를 만들고 현재 단계, 확정 결정, 남은 확인, 가정, 마지막 사용자 결정을 기록한다. 기존 프로젝트 문서 규칙이 있으면 그 규칙을 우선한다.

SPEC은 다음을 포함한다.

- 사용자·문제·핵심 흐름
- MVP·비목표
- 메뉴·화면·이동
- 입력·출력·데이터·상태·예외
- 구현 형태·운영 조건
- 성공 기준·완료 체크리스트

핵심 흐름, 입력과 결과, 예외, MVP/비목표, 성공 기준, 구현 형태가 결정되고 모호함이 약 15% 이하이며, 최종 시안 제안과 사용자의 동의·거부 또는 `NOT RUN` 사유가 기록됐을 때만 LOCK을 제안한다. 메뉴·화면·대시보드 논의와 최종 시안 제안이 끝나기 전에 SPEC 1.0 확정 질문을 먼저 하지 않는다. LOCK 후에는 임의 수정하지 않는다. 세부 규칙은 `references/spec-lock.md`와 `references/spec-template.md`를 읽는다.

## 8. 구현 승인과 검증

LOCK 직후 자동으로 코딩하지 않는다.

> 명세가 구현 가능한 수준으로 정리됐습니다. 이 SPEC을 기준으로 실제 구현까지 진행해드릴까요?

사용자가 동의하면 `IMPLEMENTATION_CONTRACT.md`를 기준으로 구현한다. 구현 후에는 실제 빌드·실행·테스트·화면·데이터 결과를 SPEC과 비교한다.

결과는 정확히 다음 중 하나다.

- `PASS`: 실제 실행하여 만족 확인
- `FAIL`: 실제 실행했으나 불만족
- `NOT RUN`: 실행하지 않음 또는 환경 없음
- `BLOCKED`: 외부 조건 때문에 진행 불가

세부 규칙은 `references/implementation-contract.md`와 `references/verification-policy.md`를 읽는다.

### 응답 종결과 핸드오프

모든 코칭 응답은 진행 내용을 요약하는 것만으로 끝내지 않는다. 응답 마지막에 반드시 현재 단계와 사용자의 다음 행동을 명시한다.

- 핵심 결정이 남아 있으면 `다음 질문`을 한 개의 구체적인 질문이나 선택지로 끝낸다.
- 최종 시안 피드백까지 끝났지만 SPEC 1.0이 확정되지 않았으면 `SPEC 1.0으로 확정할까요?`를 묻는다.
- SPEC LOCK이 끝났지만 앱을 구현하지 않았으면 `현재 상태: 명세 코칭 완료 / 앱 구현 전`이라고 알리고 `이 SPEC으로 구현까지 진행할까요?`를 묻는다.
- 사용자가 구현을 원하지 않거나 중단하면 `명세 코칭을 여기서 마칩니다`라고 종료 상태를 명시하고, 나중에 이어갈 기준을 한 줄로 남긴다.
- 구현·검증까지 끝났으면 `PASS`·`FAIL`·`NOT RUN`·`BLOCKED` 상태와 남은 조치를 명시한다.

최소 형식:

```text
현재 단계: [인터뷰 / 최종 시안 대기 / SPEC 1.0 확정 전 / SPEC LOCK / 앱 구현 전 / 검증]
다음 행동: [사용자가 답할 질문·선택지 또는 완료 상태]
```

요약만 남기고 후속 질문이나 종료 선언 없이 턴을 끝내는 것은 `FAIL`이다.

## 9. 공존과 모델 정책

다른 Skill, `AGENTS.md`, 테스트 체계, 계획·실행 하네스가 있으면 삭제·덮어쓰기·비활성화하지 않는다. 필요한 경우 확정 SPEC, 비목표, 완료 계약, 검증 기준만 전달한다. `references/coexistence.md`를 읽는다.

특정 설계 모델이나 이미지 모델을 고정하지 않는다. 모델 변경은 문장 일치가 아니라 행동 계약 eval로 확인한다.
