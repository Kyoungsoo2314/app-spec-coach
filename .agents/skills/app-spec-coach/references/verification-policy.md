# 검증 정책

## 완료 루프

```text
확정 SPEC
→ 실제 구현
→ 빌드
→ 실행
→ 테스트
→ 화면·데이터·결과 확인
→ SPEC과 비교
→ 결과 기록
```

## 결과 상태

- `PASS`: 실제 실행하여 기준을 만족함
- `FAIL`: 실제 실행했으나 기준을 만족하지 못함
- `NOT RUN`: 실행하지 않았거나 필요한 환경이 없음
- `BLOCKED`: 권한·외부 서비스·환경 등 외부 조건 때문에 진행할 수 없음

`NOT RUN`이나 `BLOCKED`를 낙관적으로 `PASS`로 바꾸지 않는다.

## 검증 순서

1. 정적 점검: 파일, 설정, 타입, 링크, 문서 구조
2. 기능 점검: 실제 입력·저장·재조회·수정·예외
3. 화면 점검: 주요 화면, 반응형, 이동, 오류 피드백
4. SPEC 비교: 각 완료 조건에 증거를 연결

화면 캡처 하나는 화면이 존재한다는 증거일 뿐, 내부 텍스트·데이터·동작을 모두 검증했다는 뜻이 아니다.

## 기록 형식

```markdown
## Verification run — [날짜]

| 기준 | 상태 | 증거 |
|---|---|---|
| 등록 후 재조회 | PASS | [명령·스크린샷·로그] |
| 모바일 저장 버튼 | NOT RUN | 실제 기기 없음 |
| 외부 문자 연동 | BLOCKED | 인증 정보 없음 |
```

## 실패 처리

- FAIL은 구현 오류인지 SPEC 미정인지 분류한다.
- 구현 오류면 범위를 바꾸지 않고 수정 후 다시 검증한다.
- SPEC 미정이면 사용자에게 질문하고 버전 변경 여부를 기록한다.
- 외부 조건이 사라질 때까지 진행할 수 없으면 BLOCKED로 남긴다.
