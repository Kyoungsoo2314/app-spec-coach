# 업무 흐름과 화면 도출

## 업무 흐름 먼저

사용자에게 처음부터 “어떤 메뉴가 필요하세요?”라고 묻지 않는다. 먼저 실제 업무 장면을 시작부터 끝까지 정리하고, 그 흐름에서 메뉴와 화면을 도출한다.

```text
상황 발생
→ 입력·기록
→ 저장
→ 목록·검색
→ 상세 확인
→ 판단·다음 행동
→ 상태 변경
→ 완료·이력
```

앱마다 모든 단계가 필요한 것은 아니다. 필요 없는 단계는 “필요 없음이 확인됨”으로 기록한다.

## 용어

- **메뉴**: 최상위 업무 영역
- **화면**: 목록, 등록, 상세, 수정, 설정, 모달 등 사용자가 보는 단위
- **이동**: 사용자의 행동에 따른 화면 사이의 경로
- **업무 흐름**: 실제 일을 처리하는 시간 순서

## 화면 완전성 질문

각 흐름에 대해 다음을 확인한다.

- 입력 후 실제 저장되는가?
- 저장한 기록을 다시 찾을 수 있는가?
- 목록에서 필요한 요약을 볼 수 있는가?
- 상세 정보를 확인할 수 있는가?
- 잘못 입력한 내용을 수정할 수 있는가?
- 삭제·취소·보류 후 상태가 어떻게 되는가?
- 저장 성공·실패를 사용자가 알 수 있는가?
- 다음 담당자에게 어떤 정보가 전달되는가?

## 최소 메뉴 도출 예시

확정 업무가 “상품 입고 → 현재 재고 확인 → 부족 상품 보충 요청”이라면 최소 메뉴는 다음처럼 제안할 수 있다.

```text
재고
├── 재고 목록
├── 입고 기록
└── 보충 요청
```

대시보드·통계·알림은 사용자의 실제 판단에 필요하다는 근거가 있을 때만 추가한다.

## 저장 구조 질문

기술 이름을 먼저 고르지 않는다. 다음을 확인한 뒤 적합한 구조를 제안한다.

- 한 사람의 한 기기에서 쓰는가?
- 여러 기기나 여러 사람이 동시에 쓰는가?
- 인터넷 없이도 계속 써야 하는가?
- 데이터가 사라지면 복구해야 하는가?
- 기존 시스템과 연동해야 하는가?

가능한 후보를 제안할 때는 선택 이유와 운영상 주의점을 SPEC에 기록한다. SQLite 파일을 여러 클라이언트가 직접 공유해서 동시에 쓰는 구조를 기본안으로 삼지 않는다.
