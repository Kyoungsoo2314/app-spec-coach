# SPEC LOCK 정책

## LOCK 전 체크

다음 항목에 모두 답할 수 있어야 한다.

- [ ] 누가 언제 쓰는가
- [ ] 어떤 문제를 해결하는가
- [ ] 시작부터 완료까지 핵심 업무 흐름이 연결되는가
- [ ] 무엇을 입력하고 어떤 결과를 보는가
- [ ] MVP와 비목표가 구분되는가
- [ ] 메뉴·화면·이동이 흐름과 연결되는가
- [ ] 주요 예외·중복·수정·삭제가 결정되는가
- [ ] 데이터 보존·백업·권한 필요성이 확인되는가
- [ ] 구현 형태와 운영 환경이 결정되는가
- [ ] 성공 기준이 실제로 검증 가능한가
- [ ] 현재 모호함이 약 15% 이하인가
- [ ] 사용자 판단이 필요한 핵심 미확정 사항이 없는가

## LOCK 행동

조건을 만족하면 SPEC에 다음을 기록하고 사용자에게 구현을 제안한다.

```yaml
status: locked
spec_version: 1.0
```

LOCK은 구현 시작 명령이 아니다. 반드시 다음 의미의 승인을 기다린다.

> 명세가 구현 가능한 수준으로 정리됐습니다. 이 SPEC을 기준으로 실제 구현까지 진행해드릴까요?

## 구현 중 분류

### 구현 오류

SPEC이 명확하고 코드·설정·테스트가 틀린 경우다. 사용자에게 새 요구사항을 묻지 말고 코드 수정과 검증으로 처리한다.

### SPEC 미정

구현을 하려면 사용자의 판단이 필요한 빈칸을 발견한 경우다. 해당 부분을 멈추고 짧은 질문으로 확인한다. 결정 전에는 임의로 LOCK된 SPEC을 바꾸지 않는다.

### 확장 아이디어

유용하지만 LOCK된 SPEC에 없는 기능이다. 구현하지 않고 `확장 후보`로 기록한다.

## 변경

중요한 사용자 승인 변경은 새 버전으로 기록한다.

```text
SPEC 1.0
→ 사용자 승인 변경: 보충 요청을 별도 상태로 관리
→ SPEC 1.1
```

기존 결정, 변경 이유, 영향 받는 구현 계약을 함께 기록한다.
