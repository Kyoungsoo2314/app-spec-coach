# 초보자 사전 시각 checkpoint 정책

## 목적

이미지는 예쁜 화면을 만드는 장식이 아니라, 사용자가 “이 화면으로 실제 일을 할 수 있나?”를 판단하도록 돕는 참고자료다.

## 기본 원칙

이미지 생성은 초보자가 기능을 먼저 알아야 요청할 수 있는 선택 메뉴가 아니다. 핵심 업무 흐름과 최소 화면이 정리된 뒤, 최종 SPEC 1.0을 확정하기 전에 기본으로 한 번 보여준다.

사용자가 명시적으로 건너뛰겠다고 하거나 이미지 capability가 없는 경우에만 생략한다.

## 실행 조건

다음 조건이 대체로 맞을 때만 제안한다.

- 핵심 업무 흐름이 정리됨
- 최소 메뉴와 주요 화면이 정리됨
- 약식 모호함이 약 30~40% 이하
- 이미지가 텍스트 설명보다 판단에 실제로 도움이 됨
- 사용자가 초보자·처음 사용자이거나 이미지 기능을 모를 가능성이 있음

대시보드가 필요 없는 앱에 대시보드를 억지로 넣지 않는다.

## 안내 형식

```text
핵심 업무 흐름과 화면 구조가 어느 정도 잡혔습니다.
최종 명세로 잠그기 전에 가장 중요한 화면을 실제 앱처럼 먼저 보여드리겠습니다.
먼저 [업무 영향이 가장 큰 화면]을 시안으로 확인하겠습니다.
```

사용자에게 이미지 기능을 알고 있는지 묻지 않는다. 화면을 고를 때 결과가 크게 달라지는 경우에만 핵심 화면 선택 질문 하나를 하고, 그렇지 않으면 업무 영향이 가장 큰 화면 하나를 합리적으로 선택한다.

## 같은 턴 실행 계약

1. `STATE`에 `visual_checkpoint: pending`을 기록한다.
2. 확정된 SPEC v0.1과 화면 구조만으로 이미지 prompt를 만든다.
3. 현재 tool context에 호출 가능한 이미지 capability가 있으면 **그 턴 안에서 실제 도구를 호출한다**.
4. 도구 결과 이미지와 함께 이미지가 요구사항의 진실의 기준이 아님을 설명한다.
5. 사용자의 화면 피드백을 받는다.
6. 피드백 중 업무 규칙·필수 정보·이동 변경만 SPEC 1.0에 반영한 뒤 LOCK을 검토한다.

실제 호출 없이 “이미지를 만들겠다”고만 답하고 턴을 끝내는 것은 `FAIL`이다.

## capability 정책

현재 실행 환경에서 제공하는 이미지 생성 capability를 사용한다. 가능한 경우 사용 가능한 `$imagegen`을 같은 턴에 호출한다. 특정 내부 모델 ID, 품질 설정, 자동 최신 모델 여부를 이 Skill의 핵심 계약으로 만들지 않는다.

이미지 capability가 없거나 호출에 실패하면 `NOT RUN` 사유를 STATE에 기록하고 다음으로 진행한다.

```text
텍스트 화면 구조
→ SPEC 작성
→ 구현
```

실패를 사용자의 명세 부족으로 돌리지 않는다.

## 이미지의 진실성

이미지에 임의로 들어간 카드, 통계, 버튼, 메뉴, 필드, 자동화, 상태값은 SPEC에 없는 한 요구사항이 아니다. 이미지와 SPEC이 충돌하면 SPEC을 따른다.

이미지는 “참고자료”로 저장하고, 실제 요구사항 변경은 사용자에게 확인한 뒤 STATE와 SPEC 버전에 기록한다. 이미지에만 있는 기능은 자동으로 추가하지 않는다.

## 피드백 질문

```text
실제로 이 화면으로 일한다고 생각하면 가장 먼저 바꾸고 싶은 것은 무엇인가요?

① 정보가 너무 많다
② 필요한 정보가 빠졌다
③ 버튼이나 업무 순서가 다르다
④ 이 정도면 맞다
⑤ 직접 설명
```

피드백 중 업무 규칙·필수 정보·이동 변경만 SPEC 변경 후보로 올린다. 색상 취향만으로 LOCK된 기능 범위를 바꾸지 않는다.
