# 선택적 시각 검토 정책

## 목적

이미지는 예쁜 화면을 만드는 장식이 아니라, 사용자가 “이 화면으로 실제 일을 할 수 있나?”를 판단하도록 돕는 참고자료다.

## 제안 조건

다음 조건이 대체로 맞을 때만 제안한다.

- 핵심 업무 흐름이 정리됨
- 최소 메뉴와 주요 화면이 정리됨
- 약식 모호함이 약 30~40% 이하
- 이미지가 텍스트 설명보다 판단에 실제로 도움이 됨
- 사용자가 보기를 원하거나 동의함

대시보드가 필요 없는 앱에 대시보드를 억지로 넣지 않는다.

## 제안 형식

```text
핵심 업무 흐름과 화면 구조가 어느 정도 잡혔습니다.
실제 앱처럼 한 번 보시겠어요?

① 핵심 목록 화면
② 입력·등록 화면
③ 상세·처리 화면
④ 지금은 이미지 없이 계속
```

한 번에 핵심 화면 하나를 우선한다.

## capability 정책

현재 실행 환경에서 제공하는 이미지 생성 capability를 사용한다. 가능한 경우 사용 가능한 `$imagegen`을 호출할 수 있다. 특정 내부 모델 ID, 품질 설정, 자동 최신 모델 여부를 이 Skill의 핵심 계약으로 만들지 않는다.

이미지 capability가 없거나 호출에 실패하면 다음으로 진행한다.

```text
텍스트 화면 구조
→ SPEC 작성
→ 구현
```

실패를 사용자의 명세 부족으로 돌리지 않는다.

## 이미지의 진실성

이미지에 임의로 들어간 카드, 통계, 버튼, 메뉴, 필드, 자동화, 상태값은 SPEC에 없는 한 요구사항이 아니다. 이미지와 SPEC이 충돌하면 SPEC을 따른다.

이미지는 “참고자료”로 저장하고, 실제 요구사항 변경은 사용자에게 확인한 뒤 STATE와 SPEC 버전에 기록한다.

## 피드백 질문

```text
실제로 이 화면으로 일한다고 생각하면 가장 먼저 바꾸고 싶은 것은 무엇인가요?

① 정보가 너무 많다
② 필요한 정보가 빠졌다
③ 버튼이나 업무 순서가 다르다
④ 이 정도면 맞다
⑤ 직접 설명
```

피드백 중 업무 규칙·필수 정보·이동 변경만 SPEC 변경 후보로 올린다. 색상 취향만으로 LOCK된 기능 범위를 바꾸지 않는다.
