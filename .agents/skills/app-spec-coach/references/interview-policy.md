# 인터뷰 정책

## 목표

사용자에게 긴 설문을 완성하게 하는 것이 아니라, 구현 결과를 크게 바꾸는 미확정 결정을 짧은 대화로 확인한다.

## 시작 절차

1. 사용자의 아이디어를 한 문장으로 재정의한다.
2. 확인되지 않은 부분은 괄호나 “아직 확인되지 않음”으로 표시한다.
3. 현재 모호함을 약식으로 표시한다.
4. 다음 질문 하나를 고른 이유를 내부적으로 판단한다.

재정의 형식:

> 이 앱은 `[사용자]`가 `[문제]`를 해결하기 위해 `[핵심 기능]`을 사용하는 앱입니다.

## 질문 수

- 기본: 1~3개
- 새 주제의 첫 질문: 가능하면 1개
- 사용자가 “한 번에 물어봐줘”라고 요청: 최대 5개
- 답변이 길어도 다음 질문을 무조건 여러 개 붙이지 않음

## 질문 선택

질문의 우선순위는 다음을 곱해 판단한다.

```text
미확정 정도 × 업무 영향도 × 이후 설계에 미치는 영향
```

다음 주제를 순서대로 고정하지 않는다. 이미 충분히 확인된 주제는 건너뛰고 결과를 가장 크게 바꾸는 결정을 먼저 묻는다.

### 먼저 확인할 가능성이 큰 것

- 누가 언제 사용하는가
- 지금 어떤 업무 장면에서 막히는가
- 기록을 어디서 가져오는가
- 입력 후 어떤 결과를 보고 다음 행동을 하는가
- 여러 사람이 함께 쓰는가
- 데이터가 사라지면 얼마나 중요한가

### 뒤로 미룰 가능성이 큰 것

- 색상·아이콘 같은 장식
- 모델·프레임워크 이름
- 미래에 넣을 수 있는 부가 기능

## 선택형 질문

선택지는 사용자의 실제 상황으로 쓴다.

```text
현재 기록은 주로 어디에 있나요?

① Excel/스프레드시트
② 종이
③ 기존 업무 프로그램
④ 여러 곳에 흩어져 있음
⑤ 아직 기록하지 않음
⑥ 기타 또는 직접 설명
```

정답처럼 보이는 선택지를 만들지 않는다. 언제든 직접 설명할 수 있게 한다.

## 기술 질문 변환

기술 질문을 업무 질문으로 바꾼다.

| 기술 용어 | 업무 상황 질문 |
|---|---|
| PostgreSQL | 여러 사람이 동시에 같은 기록을 보고 수정하나요? |
| JWT/RBAC | 사람마다 볼 수 있거나 할 수 있는 일이 다른가요? |
| soft delete | 삭제한 기록을 나중에 복구하거나 이력을 확인해야 하나요? |
| REST API | 다른 프로그램과 정보를 주고받아야 하나요? |
| 파일 업로드 | 사진·문서·영수증 원본을 앱에 보관해야 하나요? |
| 배포 | 어느 컴퓨터에서 누가 실제로 사용할 예정인가요? |

기술을 결정해야 할 때는 답을 바탕으로 선택지를 제안하고, 최종 선택과 이유를 SPEC에 기록한다.

## 인터뷰 중단·우회

사용자가 답하기 어렵다고 하면 선택지를 더 작게 나누거나 예시 상황을 준다. 인터뷰를 거부하고 바로 만들고 싶어 하면 다음 세 가지를 먼저 적는다.

1. 임시 가정
2. 최소 완료 기준
3. 나중에 바꾸면 영향이 큰 결정

그 뒤 사용자가 요청한 범위 안에서 초안을 만든다.

## 상태 저장

앱 프로젝트 안에 `.app-spec-coach/STATE.md`가 있으면 먼저 읽는다.

```markdown
## 현재 단계
INTERVIEW

## 확인된 결정
- ...

## 남은 확인
- ...

## 현재 모호함
약 55%

## 중요한 가정
- ...

## 마지막 사용자 결정
- ...
```

이미 확인된 결정을 다시 묻지 않으며, 사용자가 결정을 바꾸면 변경 이유를 기록한다.
