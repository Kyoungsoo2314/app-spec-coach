# 수동 스모크 테스트

아래 테스트는 Skill을 Codex에 설치한 뒤 새 대화에서 수행한다. 아직 실행하지 않았다면 결과는 `NOT RUN`이다.

## S01 — 신규 앱 요청

입력:

```text
재고관리 앱 만들어줘.
```

기대:

- 바로 코드 작성 대신 명세 정리를 제안한다.
- 선택 경로를 제공한다.
- 사용자가 동의하기 전까지 구현을 시작하지 않는다.

## S02 — 쉬운 인터뷰

사용자:

```text
같이 정리하자.
```

기대:

- 한 문장 재정의를 먼저 한다.
- 현재 모호함을 `약 N%`로 표시한다.
- 첫 질문은 기술 선택이 아닌 실제 업무 상황의 선택형 질문이다.

## S03 — 반복 질문 방지

사용자:

```text
기록은 지금 Excel에 있어.
```

기대:

- 저장 위치를 확인된 결정으로 기억한다.
- 같은 질문을 다시 하지 않는다.
- 다음 업무 영향이 큰 결정으로 이동한다.

## S04 — 이미지 선택 경로

업무 흐름과 주요 화면을 정리한 뒤:

```text
목록 화면을 이미지로 한번 보고 싶어.
```

기대:

- 사용자 동의와 시각 검토의 목적을 확인한다.
- 현재 환경의 이미지 capability를 선택적으로 사용한다.
- 이미지에만 있는 기능을 SPEC에 자동 추가하지 않는다.

## S05 — 이미지 불가 경로

이미지 capability를 사용할 수 없거나 실패하는 환경에서 같은 요청을 수행한다.

기대:

- 텍스트 화면 구조와 SPEC 작성을 계속한다.
- 이미지 실패를 전체 작업 실패로 보고하지 않는다.

## S06 — SPEC LOCK과 승인

핵심 결정이 끝난 뒤:

기대:

- SPEC LOCK 조건을 요약한다.
- 구현 계약을 만든다.
- “이 SPEC으로 구현까지 진행할까요?”라고 별도로 묻는다.

## S07 — 검증 상태

브라우저·외부 서비스가 없는 상태에서 완료 보고를 요청한다.

기대:

- 실행하지 않은 항목은 `NOT RUN` 또는 `BLOCKED`다.
- 실제 실행한 항목만 `PASS`다.

## S08 — 초보자 사전 시각 checkpoint

핵심 업무 흐름과 MVP 화면이 정리됐지만 사용자가 이미지 생성을 먼저 요청하지 않은 상태에서 진행한다.

기대:

- SPEC 1.0 확정 질문보다 먼저 핵심 화면을 시안으로 보여주겠다고 안내한다.
- 이미지 capability가 있으면 같은 턴에 실제 이미지 도구 호출과 결과가 나온다.
- 이미지에만 있는 기능을 요구사항으로 자동 추가하지 않는다.
- 이미지 capability가 없으면 `NOT RUN` 사유를 남기고 텍스트 흐름을 계속한다.
